# Local versioned C2 dietary scenario API

`POST /interventions/baseline-c1-v2` accepts the existing invented `ManualC1Request` category contract (`TEST-` plus four digits, for example `TEST-0014`). It requires local access, calls genuine C1 exactly once with demo fallback disabled, and returns `assessment`, original `prediction`, `c1_calls: 1`, an input fingerprint and limitations. A C1 outage returns 503; no fabricated fallback is used.

`POST /interventions/diet-scenarios-v2` accepts `contract_version: "c2-diet-scenarios-v2"`, `age_months`, read-only `original_c1`, `feeding`, `household` and `max_candidates` (1–5). Feeding requires exact C1 meal/diversity category strings, a list of reported food groups and provenance (`unverified`, `confirmed_caregiver_report`, `direct_observation`). Household contains an actual budget and period, budget provenance, restriction state and excluded food IDs, preparation state, and per-food local availability claims. Unknown values remain unknown. Extra fields are rejected.

The response returns unchanged original C1 context, `c1_candidate_calls: 0`, baseline, age/source scope, evidence registry, `ranked_cards`, `unresolved_or_rejected`, referral notice, ranking trace and research limitations. Each comparison has a stable ID, food groups, source-linked ingredient prices, indicative period cost, illustrative seven-day food pairings, status, and pass/fail/unknown check trace. There are **no per-candidate C1 predictions**. The old routes remain versioned legacy workflows and are not silently repurposed.

The local-only check is a research boundary, not patient-record authorization. Do not send identifiable children or private PHM data through the invented-input form. A caller-supplied `original_c1` is labelled as supplied context; only the paired baseline endpoint actually verifies a live C1 response. Neither endpoint grants clinical or research approval.
# Counterfactual method selection addendum

`POST /interventions/diet-scenarios-v2` accepts `method` as `bounded_search` (default), `face_graph`, `dice`, `wachter`, or `compare_all`. The response includes the selected method and `method_results`. Each method result reports status, generated count, independently checked count, verified ranked count, unresolved/rejected count, runtime in milliseconds, and method diagnostics. FACE diagnostics include food-transition paths and pruning counts. A method whose required target or data is unavailable returns an explicit unavailable status and zero candidates. `compare_all` deduplicates equivalent ingredient sets and keeps `generator_methods` on each candidate. Runtime varies between calls; decision outputs remain deterministic for unchanged evidence and inputs.

`research_algorithm_demo` defaults to `false`. When `true`, DiCE and Wachter run only against an engineering budget-and-exclusion fixture. The separate `software_test_ranked` response field gives test-only ranks; it must never be relabelled as verified nutritional suitability or a health improvement. The independently validated `ranked_cards` field retains the full hard evidence gates. A budget with no compatible catalogue option yields an empty test rank rather than a fabricated card.
